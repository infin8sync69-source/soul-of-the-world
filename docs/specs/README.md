## How a specification is written

1. Normative text uses MUST, SHOULD and MAY as in RFC 2119.
2. Every structure has a field table with types and limits.
3. Every validation rule is numbered so tests can cite it.
4. A "Known gaps" section lists what the spec does not yet cover. A gap is not hidden.
5. A specification is not **Accepted** until: two independent implementations (or one implementation and an independent review of the vectors) reproduce the vectors, and the threat model has been reviewed against it.

## Versioning and protocol breaks

Each spec has a version. While a spec is at 0.x it MAY change incompatibly, but only with a changelog entry and regenerated vectors. After 1.0, any change that invalidates existing signed data or changes an existing Bucks ID is a **protocol break** and needs a new version number in the encoded data (the `v` field) and a migration plan.

## Test vectors

Vectors in [spec/test-vectors](../../spec/test-vectors) are generated by the reference implementation in `core/bucks-core` and **independently verified** by `scripts/verify_vectors.py` (Python, separate CBOR codec, separate crypto libraries). Both run in CI. Each vector file names its secrets: they are test keys derived from labels and **must never be used for anything real**; the verifier fails if a listed secret is not BLAKE3 of its label.

Acceptance status: the independent-verification half of the acceptance rule is met for 0.2. Threat-model review and an external review are still needed before Accepted.

Changing a vector is a protocol break and must be called out in the pull request title.
